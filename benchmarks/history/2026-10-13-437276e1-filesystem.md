# S3 filesystem benchmark of the PyAthena 4.1.0 release commit on 2026-10-13

This entry records the [filesystem suite](../README.md#filesystem-suite) at commit [`437276e1`](https://github.com/pyathena-dev/PyAthena/tree/437276e18c22a3f508c9d436f8e9fa4a0096d439/benchmarks), the commit planned for the PyAthena 4.1.0 release, for #685.
It compares S3 transfers through `S3FileSystem`, whose files run parallel requests in an `S3ThreadPoolExecutor`, with `AioS3FileSystem`, whose files run them through `S3AioExecutor`, at two values of the filesystem's `max_workers` and two sizes of the S3 client's connection pool.
The cursor run of the same commit is a [separate entry](2026-10-13-437276e1.md).

## Selection

The suite ran as the [README](../README.md#filesystem-suite) selects it for `c8gn.2xlarge`: 16 jobs, five repetitions, no warmups.

- **small, medium, large**: reads and writes.
- **xlarge**: writes and copies; reads of the 6 GiB object were left out because a read holds about twice the object in memory, and copies of objects up to 5 GiB are single CopyObject requests.

Each operation ran with the sync and aio APIs, `max_workers` 8 and 40, and connection pools (`max_pool_connections`) of 10 and 40.
The sync API calls the filesystem on the trial's thread; the aio API runs reads and writes in `asyncio.to_thread()`, as `AioS3FSCursor` does, so that a file's parallel requests go through `S3AioExecutor` on fsspec's event loop, and awaits the copy coroutine on the trial's event loop.

## Run record

The queue `fs-1` was published at 13:31 UTC, and its 16 jobs finished on the one host by 13:58 UTC without an interruption.
Each of the 64 cases recorded five successful trials and no failure.

## Findings

1. **Reads performed alike with both APIs.**
   For the 1 GiB object, sync read 432 to 565 MiB/s and aio 448 to 590 MiB/s; with 40 workers, aio read 4 to 6% faster.
2. **With 40 workers, aio writes and copies were capped by the event loop's default executor.**
   For the 6 GiB object, sync wrote 861 to 864 MiB/s and aio 647 to 665 MiB/s (0.75 to 0.77 times sync); for the 1 GiB object, 712 to 718 against 575 to 593 MiB/s.
   Sync copied the 6 GiB object at 1,495 to 1,781 MiB/s and aio at 521 to 540 MiB/s (0.30 to 0.35 times).
   The sync processes peaked at 51 threads and the aio processes at 24 to 25, as the 12-thread default executors bound the aio requests.
3. **With 8 workers, aio matched or exceeded sync.**
   Writes of the 6 GiB object ran at 470 to 497 MiB/s with both APIs, and aio copies ran at 366 to 390 MiB/s against 267 to 274 MiB/s for sync; the cause of the copy difference was not investigated.
4. **The connection pool size made no consistent difference.**
   botocore's urllib3 pools do not block: when every pooled connection is in use, a request opens another connection, which is discarded afterwards, so a pool of 10 did not limit 40 workers; the largest difference between pools of 10 and 40 at the same other settings was the sync copy with 40 workers (1,495 against 1,781 MiB/s).
5. **A write held about the whole object in memory.**
   Writing the 6 GiB object peaked at 6,005 to 6,313 MiB with both APIs, and the 1 GiB object at 1,245 to 1,376 MiB: `S3File` submits each part to its executor without waiting, so parts that wait for an upload slot stay in memory when the writer is faster than the uploads.
6. **Small objects were dominated by per-request overhead.**
   For 64 MiB, both APIs read at 202 to 312 MiB/s and wrote at 146 to 180 MiB/s, without a consistent order among the settings.

For #685, the aio path performs like the sync path up to the default executor's thread count, and falls behind for writes and copies with more workers than that.

## Limits

- One host and five trials per case; one `c8gn.2xlarge` host in one Availability Zone.
- The objects hold zero bytes; S3 does not compress them, but other content was not measured.
- Reads of the 6 GiB object did not run, and copies only ran at 6 GiB.
- The aio cap depends on the host's CPU count; other instance sizes change it.
- Cursor reads through `AioS3FSCursor` were measured in the [4.0.0 run](2026-10-11-8a69ce03.md), not in this run.
